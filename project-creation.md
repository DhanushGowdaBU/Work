# NYBOSS Project Creation

This document defines how NYBOSS .NET projects are created.

The current stage creates the project skeleton and initial structural files.

The goal is to create:

- projects
- folders
- structural files
- project configuration
- project references
- solution entries

Business implementation is not part of this stage.

---

# Target Framework

All newly generated projects must target:

net8.0

Use the framework explicitly when creating projects.

Do not allow the latest installed SDK/framework to determine the target framework automatically.

---

# Default Business Project

When the user requests a:

- simple project
- basic project
- normal project
- standard project
- regular project
- default project
- Business project without specifying components

create:

<ProjectName>.API
<ProjectName>.Common
<ProjectName>.Repository
<ProjectName>.Services

under:

Apps/Business/<ProjectName>/

---

# API Project

Create:

<ProjectName>.API

using the controller-based ASP.NET Core Web API template.

Use:

dotnet new webapi --framework net8.0 --use-controllers --name <ProjectName>.API

The generated API project must contain:

<ProjectName>.API/
├── Controllers/
├── Properties/
│   └── launchSettings.json
├── appsettings.json
├── appsettings.Development.json
├── appsettings.Local.json
├── build-info.json
├── <ProjectName>.API.csproj
└── Program.cs

The actual .NET template may generate additional files.

Remove:

<ProjectName>.API.http

unless explicitly requested by the user.

Do not replace or blank the content generated by the .NET template.

Keep valid CLI-generated content in:

- Program.cs
- .csproj
- launchSettings.json
- appsettings files
- other required template-generated files

Create missing NYBOSS structural files where required.

Do not create business-specific controllers.

---

# Common Project

Create:

<ProjectName>.Common

using:

dotnet new classlib --framework net8.0 --name <ProjectName>.Common

The Common project must contain:

<ProjectName>.Common/
├── Constants/
│   └── <ProjectName>Constants.cs
├── Contracts/
│   ├── Repository/
│   │   └── I<ProjectName>Repository.cs
│   └── Services/
│       └── I<ProjectName>Service.cs
├── Models/
│   └── <ProjectName>Model.cs
├── Options/
│   └── <ProjectName>Options.cs
├── GlobalUsings.cs
└── <ProjectName>.Common.csproj

These structural files ensure that the required folders are represented in the project.

The files should contain minimal valid project-specific skeleton code.

Do not implement business functionality.

Do not copy implementations from another application.

---

# Common Structural Files

Create:

Constants/<ProjectName>Constants.cs

Models/<ProjectName>Model.cs

Options/<ProjectName>Options.cs

Contracts/Repository/I<ProjectName>Repository.cs

Contracts/Services/I<ProjectName>Service.cs

These files are structural skeletons.

Use the new project name in namespaces and type names.

Do not add business-specific properties, methods, constants, or behavior unless explicitly requested.

---

# Repository Project

Create:

<ProjectName>.Repository

using:

dotnet new classlib --framework net8.0 --name <ProjectName>.Repository

The Repository project must contain:

<ProjectName>.Repository/
├── <ProjectName>Repository.cs
├── RegisterServices.cs
└── <ProjectName>.Repository.csproj

`<ProjectName>Repository.cs` is a structural repository class.

It should not contain business-specific repository implementation.

`RegisterServices.cs` is a structural registration file.

Do not copy implementation from another application.

---

# Services Project

Create:

<ProjectName>.Services

using:

dotnet new classlib --framework net8.0 --name <ProjectName>.Services

The Services project must contain:

<ProjectName>.Services/
├── <ProjectName>Service.cs
├── RegisterServices.cs
└── <ProjectName>.Services.csproj

`<ProjectName>Service.cs` is a structural service class.

It should not contain business-specific service implementation.

`RegisterServices.cs` is a structural registration file.

Do not copy implementation from another application.

---

# Structural File Content

Structural files created specifically by the generator must contain minimal valid C# skeletons.

Examples of structural types include:

- `<ProjectName>Model`
- `<ProjectName>Constants`
- `<ProjectName>Options`
- `I<ProjectName>Repository`
- `I<ProjectName>Service`
- `<ProjectName>Repository`
- `<ProjectName>Service`

Do not implement business behavior.

Do not add properties or methods unless required for the structural skeleton.

---

# CLI-Generated File Content

When `dotnet new` creates a file, preserve its generated content.

Do not:

- empty it
- replace it with a placeholder
- recreate it from scratch unnecessarily
- copy content from another project

Only modify CLI-generated files when required to satisfy project-generation requirements.

Examples of allowed modifications include:

- project references in `.csproj`
- target framework configuration
- project naming configuration

---

# Default Project References

For the default composition:

<ProjectName>.API
<ProjectName>.Common
<ProjectName>.Repository
<ProjectName>.Services

create:

<ProjectName>.API
    -> <ProjectName>.Services

<ProjectName>.Services
    -> <ProjectName>.Common
    -> <ProjectName>.Repository

<ProjectName>.Repository
    -> <ProjectName>.Common

Use:

dotnet add <project> reference <referenced-project>

The references must point to components belonging to the same newly created project.

Do not reference equivalent projects from another application.

---

# Explicit Project Composition

If the user specifies components, create only those components.

For example:

"Create <ProjectName> with API, Common and Services"

creates:

<ProjectName>.API
<ProjectName>.Common
<ProjectName>.Services

Do not create Repository because it was not requested.

Create only the folders and structural files applicable to the selected components.

Only add project references that are valid for the selected components.

Do not add references to components that do not exist.

---

# Similar Project

If the user requests:

"Create <ProjectName> similar to <ExistingProject>"

the existing project is used as a STRUCTURAL REFERENCE ONLY.

Inspect the reference project to determine:

- project composition
- project types
- project directories
- folder names
- subfolder names
- file names
- file locations
- applicable project-to-project relationships

Use this information to create the new project structure.

---

# Similar Project Structure Process

For a similar-project request:

1. Locate the reference project.
2. Determine its project components.
3. Determine the type of each component.
4. Determine the directory hierarchy.
5. Determine the file hierarchy.
6. Create equivalent new projects.
7. Apply the new naming convention.
8. Recreate the folder hierarchy.
9. Recreate the file hierarchy.
10. Create structural files required for folders that would otherwise be empty.
11. Recreate applicable internal project references.
12. Add all generated projects to the existing solution.
13. Preserve content generated by the .NET CLI for newly created projects.
14. Do not copy implementation from the reference project.

---

# Similar Project File Rule

If the reference project contains:

<Folder>/<File>

create the corresponding:

<ProjectName>.<Component>/<Folder>/<File>

where applicable.

Reproduce:

- file name
- file location
- extension

Do not copy the contents of the reference file.

If the corresponding file is generated by a .NET CLI template, keep the CLI-generated content instead of replacing it with blank content.

If the file is a new structural file created specifically to represent the structure, create minimal valid skeleton content.

---

# Project Configuration

Generated `.csproj` files must:

- use the new project name
- target net8.0
- contain applicable project references
- contain only required configuration for the generated project

Do not blindly copy an existing application's `.csproj`.

Do not copy unrelated package references.

Do not copy unrelated project references.

Do not copy application-specific configuration.

Keep the content generated by the CLI unless a required project-generation modification is needed.

---

# Solution

Use:

BNPP.NYBOSS.NextGen.Server.sln

Add every generated project using:

dotnet sln BNPP.NYBOSS.NextGen.Server.sln add <project-path>

Do not create a separate solution.

---

# Unwanted Template Files

The default API project must not contain:

<ProjectName>.API.http

If the .NET template generates this file, remove it after project creation.

Do not remove other required files generated by the template.

---

# Structure-Only Completion

Project creation is complete when:

- requested projects exist
- requested folders exist
- required structural files exist
- CLI-generated files retain their generated content
- unwanted template files are removed
- project names are correct
- project references are correct
- projects target net8.0
- projects are added to the existing solution

Do not continue into business implementation automatically.
